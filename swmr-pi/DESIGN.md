## 1. 目的

メインセッションのコンテキストを守りながら、情報収集だけを並列化する。

- **MAIN の仕事（これだけ）**: ヒアリング・要件台帳（ヒアリング層+校正層）の作成・ルーティング・人間への提示
- **planner の仕事**: 要件と調査結果から設計 + パケット作成（read-only）
- **research / inspect の仕事**: 並列スポーン。read-only で情報を集め、圧縮して返す
- **function-tester の仕事**: E2E通過後、仕様・@why・設計を読まない別プロセスでunit testを追加する
- **dev の仕事**: 直列で 1 体だけ。パケット（最小スコープの文脈）を受け取り実装する

MAIN は**設計しない・実装しない・調査しない・判断しない**。最終判断は人間が行う。
MAIN の成果物は要件台帳（ヒアリング層 + 校正層）だけ。

> **SPEC 原文との関係**: 00_SPEC-swmr.md の「Main Agent が設計・実装・最終判断を行う」は
> 本設計で再分配した（設計→planner、実装→dev、最終判断→人間）。SPEC は原則の正本として
> そのまま保存し、本設計書が pi.dev での適用形とする。
> 軽量実装（§3.1）ではこの再分配は部分的で、main が planner/dev の代行も行う。

原則の再掲（00_SPEC-swmr.md §0）:
> **コードは並列化しない。情報だけ並列化する。**
> Read は水平スケールする。Write は水平スケールさせない。

**実装方針: 方法は問わない。コスト軽い方がいい。**

この設計の目的（SWMR 運用）は、必ずしも subagent 機械を必要としない。
達成できれば方法は問わず、**最もコストの軽い実装を第一候補**とする。

- 軽量実装（第一候補・ゼロインフラ）: 要件台帳 + pi の並列ツール実行 + セッション内直列
- 重装実装（任意・自走モードのときだけ）: subagent extension（spawn 独立プロセス・文脈分離）

## 2. 運用モデル（Reader 3 種 + function-tester + dev + reviewer（任意）+ 人間）

```
Human ──(ヒアリング)──> MAIN（薄いモデルでよい・ヒアリングと要件まとめのみ）
                            │
                            ▼
                    要件台帳（ヒアリング層 + 校正層）
                            │
              ┌─────────────┼──────────────┐
              ▼             ▼              ▼
         research      inspect        planner
         (並列スポーン)  (並列スポーン)  (設計+パケット)
         read-only      read-only      read-only
              │             │              │
              └──────┬──────┘              │
                     ▼                     │
              調査結果（SWMR形式）          │
                     │                     │
                     └─────────┬───────────┘
                               ▼
                        DESIGN_PACKET.md
                               │
                               ▼
                    dev（直列・同時に1体・write可）
                               │
                               ▼
                    MAIN/WriterがE2E実行
                               │
                               ▼
             function-tester（直列・同時に1体・write可）
             E2E後にunit testを追加
                               │
                               ▼
                    MAIN/WriterがE2E再実行
                               │
                               ▼
                       reviewer（read-only・任意）
                               │
                               ▼
                    MAIN（要件との整合確認・人間へ提示）
                               │
                               ▼
                          Product
```

| 役割 | 並列性 | write 権限 | モデル | 出力 |
|---|---|---|---|---|
| MAIN | —（1体） | 有（要件台帳のみ）※軽量では実装も | **薄い会話モデルでよい** | 要件台帳（ヒアリング層+校正層） |
| research | 並列（最大8タスク・4並行） | **無** | 強 | SWMR §4 形式 |
| inspect | 並列（同上） | **無** | 強 | scout 形式 + SWMR 形式 |
| planner | 直列（main の次） | **無** | 強 | 設計 + DESIGN_PACKET.md |
| function-tester | **直列・同時に1体** | 有（指定テストファイルのみ） | 強 | Function Inventory / Unit Test Result / Unknowns |
| dev | **直列・同時に1体** | 有 | 強 | Completed / Files Changed / Evidence |
| reviewer（任意） | dev の後に直列 | **無** | 強 | Critical / Warnings / Suggestions |
| 人間 | — | 有 | 最強 | 判断 |

## 3. 実装基盤（軽量優先・方法非依存）

### 3.1 軽量実装（第一候補・ゼロインフラ）

subagent 機械なしで SWMR を実現する:

1. **要件台帳**: `REQS.md`（議事録形式）。規約のみ・ファイル 1 つ
2. **並列調査**: pi は同一メッセージで複数ツールを並列実行できる。web_search / read / bash / yspec / yhist をまとめて呼ぶ = 並列 Reader がゼロコストで実現
3. **直列実装**: 軽量では役割が分離されない。**main が planner の代行として dev 相当の実装も行う**（§1 の「MAIN は実装しない」は重装時の原則。軽量では MAIN が §5 の校正層作成に加えて実装も担う）。単発修正は AGENTS.md の「聞いて→直接やる」フローをそのまま使う
4. **モデル**: セッションのモデルのまま。切り替え不要（§8 のモデル割り当ては重装向け）
5. **write 制約**: 調査系ツール（web_search / yspec / yhist / read）は元々 read-only。規約で「調査は read-only ツールのみ」と定める
6. **レビュー**: プロンプトで「視点（perspective）」と「先入観なし（@why・設計文書を読まない）」を指定して評価させる（§4.5）。**軽量（同一セッション）では「視点の固定」が主効果で、「先入観なし」は部分的近似**（コンテキストに @why が既に含まれるため）。真の文脈ゼロは別プロセス（`pi -p --no-context-files --no-session`）または重装で達成できる

### 3.2 重装実装（任意・自走モードのときだけ）

`examples/extensions/subagent/` を使う（spawn 独立プロセス・並列/直列・JSON出力）。
長時間自走で main のコンテキストが溢れる時にのみ導入を検討する。
対話セッションでは起動コストがむしろ増えるため、軽量実装を優先する。

## 4. エージェント定義（重装実装を選んだ場合のみ）

> 軽量実装（§3.1）では subagent エージェント定義は不要。
> 以下は重装実装（§3.2）を選んだ場合の定義。

### 4.1 function-tester（Writer・直列）

function-testerは、E2Eが通った後に起動するunit-test専用のWriterである。対象ソースの仕様・@why・設計書・git履歴を読まず、指定ソースと指定テストファイルだけを読む。対象の意味のあるプロダクト関数を `tested / unknown / excluded` に分類し、指定されたテストファイルだけへunit testを追加する。

function-testerはE2Eを再実行しない。unit testの完了後、MAIN/Writerが全テストとE2Eを最初から実行し、E2E-only coverageを確認する。そこで未到達の重要な利用経路が見つかった場合、MAIN/WriterがE2Eを追加する。

`function-tester` はテストコードのhelperや生成コードを「全関数」に含めない。また、カバレッジ数値だけを増やす空テスト、既存テストの弱体化、実装に合わせただけの期待値捏造を行わない。契約がソースだけで確定しない関数は `unknown` として報告する。

無知な状態は別プロセスの `--no-context-files --no-extensions` と、タスクで指定する許可ファイルによる文脈分離である。function-testerの子プロセスは `read,write,edit` のみを有し、bashは与えない。親ラッパーが指定の `unitCommand` を実行してEvidenceを付加する。write/editは子プロセス内のガードで指定テストファイル以外をブロックする。これはファイルシステム権限サンドボックスではない。

### 4.2 research（Reader・並列）

```markdown
---
name: research
description: 外部情報調査（Web/API仕様/ライブラリ/技術比較/競合/セキュリティ）
tools: read, bash, web_search
model: <強いモデル>
---

あなたは調査エージェント。プロジェクトを変更しない。bash は read-only コマンドのみ
（curl での読み取り・git log 等。write/edit は禁止）。
調査結果は下記 JSON 形式で返せ。生ログは返さない。根拠（URL・コマンド・出力）は
evidence に必ず入れる。
{
  "facts": [],          // 確定した事実
  "constraints": [],    // 制約（バージョン・API制限・ライセンス等）
  "unknowns": [],       // 判明しなかったこと
  "conflicts": [],      // 情報源間の矛盾
  "recommendations": [],// 推奨（判断ではない。判断は人間）
  "evidence": []        // 根拠（URL・コマンド・実測）
}
```

### 4.2 inspect（Reader・並列）

```markdown
---
name: inspect
description: 既存プロジェクト内部調査（関連コード/依存/過去の設計判断/影響範囲）
tools: read, bash
model: <強いモデル>
---

あなたは調査エージェント。プロジェクトを変更しない。bash は read-only のみ
（git log / git diff / git show / yspec / yhist）。
出力は scout 形式（別エージェントが再読まなくて済む圧縮コンテキスト）:
## Files Retrieved（パスと行範囲）
## Key Code（実際のコード断片）
## Architecture（構成の説明）
## Start Here（最初に読むべき場所）
末尾に SWMR 形式の facts/constraints/unknowns/conflicts/recommendations/evidence を付ける。
```

### 4.3 planner（Reader・設計・直列）

```markdown
---
name: planner
description: 要件台帳と調査結果から設計と実装パケットを作成（read-only）
tools: read, bash
model: <強いモデル>
---

あなたは設計エージェント。プロジェクトを変更しない（要件台帳・パケットの作成は
メイン/人間の承認後に別途行う。ここでは設計文書の形で返す）。
入力: 要件台帳 + 調査結果（research/inspect の出力）
出力形式:
## Goal（1文）
## 設計判断（WHY を含む。技術選択・アーキテクチャの理由）
## 変更範囲（ファイル・関数・追加/変更内容）
## 制約（既存機能を壊さない・規約）
## 完了条件（E2E 全 PASS 等）
## DO_NOT（触ってはいけないもの）
## Risks（注意点）
```

この出力が `DESIGN_PACKET.md` の元になる。

### 4.4 dev（Writer・直列・同時に1体）

```markdown
---
name: dev
description: 実装エージェント（パケット入力・直列・write可）
model: <強いモデル>
---

あなたは実装エージェント。パケット（DESIGN_PACKET 形式）に書かれた範囲だけを実装する。
- パケットの WHY をコードに // @why: として内蔵する（Delete What, Keep Why）
- パケットに書かれたファイル・関数以外を変更しない
- 完了条件（E2E 全 PASS 等）を満たすまで修正する
- 報告は Evidence 形式: Completed / Files Changed / Notes（コマンド+出力ログ）
```

dev は **write を許可する唯一のサブエージェント**。同時に 1 体しか起動しない（直列）。

### 4.5 reviewer（Reader・視点付き・先入観なし）

レビューアの目的は「コードベースを『ある視点から』『先入観なく』評価する」こと。

**設計の要（2 つ）:**

> **実行手段の区分**: 軽量実装（同一セッション）では「視点レビュー（近似）」のみ。
> 真の「先入観なし」は別プロセス（`pi -p --no-context-files --no-session`）または重装でのみ達成できる（REQ-007 実験で実証）。

1. **ある視点から** — レビューアに「視点（perspective）」を 1 つ与える。視点が明確だと、その視点での問題が浮き彫りになる。
   - 視点の例: セキュリティ / パフォーマンス / 可読性・保守性 / アクセシビリティ / UX / エッジケース・バグ / データ整合性 / ビジネス要件との整合
   - **視点は AI（MAIN/レビューア）が決める**（REQ-006 合意済み）。人間の指定も可。
2. **先入観なく** — レビューアは**作者の意図・経緯・@why・設計文書を読まない**。コードの実体だけから評価する。
   - 作者は「これは意図的にこうした」を知っているため、問題を問題と認識しない。第三者は意図を知らないので、コードの振る舞いだけから判断できる
   - @why は実装者・保守者用（意図の伝達）、レビューアは検証者用（実体の検証）。両方あって初めて「意図の正しさ」と「実体の正しさ」の両方が検証できる

**軽量実装でのレビュー:**

```
あなたは <視点> の専門レビューア。このコードベースを初めて見る。
- @why・設計文書・経緯は読まない（先入観なし）。コードの実体だけから評価する
- <視点> の観点だけに絞って評価する
- 出力: Critical（修正必須）/ Warnings（修正推奨）/ Suggestions（改善案）
  それぞれファイル:行・問題・理由・修正案
```

**重装実装での定義:**

```markdown
---
name: reviewer
description: 視点付き・先入観なしのコードレビュー（read-only）
tools: read, bash
model: <強いモデル>
---

あなたはレビューア。与えられた視点（perspective）だけに絞ってコードベースを評価する。
@why・設計文書・作者の意図・経緯を読まない（先入観なし）。コードの実体だけから判断する。
bash は read-only のみ（git diff / git log / git show）。write は禁止。
出力:
## Reviewed（対象ファイル:行範囲）
## Critical（修正必須）: ファイル:行 - 問題 - 理由 - 修正案
## Warnings（修正推奨）: ...
## Suggestions（改善案）: ...
## Summary（2-3文）
```

## 5. E2E snowball（E2E → 全意味関数unit test → E2E-only coverage）

E2E snowballは、E2Eを増やすだけの運用ではない。次の順序で検証を累積する。

1. 新機能の外部振る舞いをE2Eで固定し、E2Eを通す。
2. `function-tester` を、仕様・@why・設計を読まない別プロセスで起動する。
3. function-testerが対象ソースの全ての意味のあるプロダクト関数を `tested / unknown / excluded` に分類し、unit testを指定テストファイルへ追加する。
4. function-testerはunit testだけを実行し、E2Eは実行しない。
5. MAIN/Writerが全unit testとE2Eを最初から実行する。
6. unit testではなく、E2Eだけで到達した関数・分岐・エラー経路を計測する。
7. E2E-onlyで未到達の重要な経路があれば、意味のある利用シナリオをE2Eへ追加する。
8. 全テストを最初から実行し、既存の保証を維持する。

単体テストは関数の局所契約・境界・異常系を保証し、E2Eは外部から見た利用シナリオとシステム接続を保証する。総合coverageとE2E-only coverageは別の値として扱う。カバレッジ数値だけを増やす空テストはsnowballではない。

### 5.1 道具: coverage-diff（手順6–7の実装）

// @why: [2026-08-27] 手順6–7（E2E-only coverage計測）は長らく文章だけだったので `coverage-diff.mjs` として道具化。
//        依存ゼロ（NODE_V8_COVERAGE）で unit / E2E の到達を別々に採取し、関数単位の差分を報告する。
//        read-only の感覚器でありカバレッジ数値でブロックしない（v1.4「ヒントであり矯正ではない」）。
// @tags: SPEC

```bash
node swmr-pi/coverage-diff.mjs --unit "node test/core.test.js" --e2e "node e2e.mjs" --source src
```

出力は関数単位の4分類と次アクションの提案:

| 分類 | 意味 | 次アクション |
|---|---|---|
| `both` | unit と E2E の両方が到達 | なし（二面保証済み） |
| `unit-only` | E2E-gap | 意味ある利用シナリオを E2E へ追加する候補（手順7） |
| `e2e-only` | unit-gap | function-tester へ委譲する候補（手順2） |
| `uncovered` | どちらも未到達 | デッドコードか完全未検証かを判断 |

exit≠0 になるのはテストコマンド自体の失敗（物理的破綻）のみ。差分の多寡ではブロックしない。
制約: node 実行のテストに限る（ブラウザ内実行のカバレッジは採れない。例: kazari-studio の Canvas 描画系は uncovered に見える）。

## 6. 要件の層構造（ヒアリング層 → 校正後ヒアリング仮定層 → 実装層）

（以下「校正後ヒアリング仮定層」を「校正層」と略記する）

MAIN の成果物は「要件台帳」。**思考ログ（LLM が意図を考えた過程）は残さない。**

思考ログは計算であって成果物ではない。価値があるのは「使う時」（校正を生む時）であり、
「残す時」ではない。誤った経路・捨てた候補が混ざり、未来の AI にとってはノイズになる
（clearify: 探させない）。

残すのは「人間の原文」と「AI の校正+仮定」の**交互**。これで
「何が言われた → どう解釈した → 何を作った」が一望できる。

### 要件台帳 = 整理した議事録

要件台帳は「整理した議事録」のようなもの。文字起こし（思考ログ）は残さず、
「発言 → 決定事項 → アクションアイテム」に圧縮して残す。

- 文字起こし = 全部残す（思考ログと同じ。ノイズ）
- **整理した議事録 = 発言 → 決定事項 → アクションアイテム**に圧縮する（台帳と同じ）

議事録の比喩が説明する 3 つのこと:

1. **議事録係は薄くていい**: 議事録係は内容を設計しない。聞いて、要点をまとめて、正確に記録するだけ。薄い MAIN 説と一致。
2. **台帳は隔離された文脈たちの唯一の共有メモリ**: subagent は文脈分離されている（互いの会話を知らない）。要件台帳が唯一の共有記憶になる。dev は校正層（合意済み）だけを読み、planner は台帳+調査結果を読み、コードの @why は台帳に接続する。議事録が「会議にいなかった人も追える」ように、台帳は「文脈を持たないサブエージェントも追える」ようにする。
3. **普通の議事録より 1 点優れている**: 決定事項だけでなく**未決定のもの（仮定・不明点・矛盾）も残す**。誤解が「仮定の誤り」として検出される。

注意:
- 台帳は生きた文書。dev が読む・@why が繋がる・REQ からコードへ辿れる状態を保つ。死んだ文書になったら失敗。
- 原文はコンパクトに。文字起こしを台帳に貼るのは思考ログを貼るのと同じ。

### 要件台帳の 1 エントリ（REQ-xxx）

```
## REQ-001 <タイトル>
- ヒアリング（原文）: 「...」 (2026-08-27, 人間)      ← そのまま残す。解釈しない
- 校正（AI 解釈）: 意図の整理。
    仮定: [...]（「□□と解釈した。違えば指摘して」）
    不明点: [...]（聞き漏らし・後で必要になること）
    矛盾: [...]（人間の要求間の衝突）
- 確認: 人間の承認 / 修正 (2026-08-27)               ← 校正層への合意
- 実装: DESIGN_PACKET-001 → dev → コード（@why に校正層の結論を内蔵）
```

### 層の定義

| 層 | 内容 | 誰が書く | 残す/捨てる |
|---|---|---|---|
| ヒアリング層 | 人間の原文（そのまま・解釈しない） | 人間 | **残す**（意図の正本） |
| 校正後ヒアリング仮定層 | AI の解釈 + 仮定 + 不明点 + 矛盾 | MAIN | **残す**（人間との合意対象） |
| 実装層 | パケット → dev → コード | planner / dev | 残す（@why が校正層と接続） |
| 思考ログ | LLM が意図を考えた過程 | LLM | **捨てる**（計算であって成果物ではない） |

### 思考ログと @why の違い

- **思考ログ** = 「どう考えたか」（過程）。捨てる。
- **@why** = 「なぜこの結論か」（結論の理由）。コードに内蔵して残す。

このワークスペースの @why 規約は既にこの区別を体現している。校正層の結論が
@why としてコードに引き継がれる。

### なぜこの構造がきれいか

- 交互に並ぶので「人間の意図 ⇄ AI の解釈」の対応が一望できる
- 校正層に仮定を明示するので、誤解が「仮定の誤り」として検出・修正できる
- dev は校正層（合意済み）だけを読めばよい。思考ログも原文のノイズも不要

## 6B. パケット方式（dev への入力・最小スコープ文脈）

dev はメインの暗黙知識を持たない。だから**パケットで文脈を明示的に渡す**（ワークスペースの worktree パケット方式 `DEBUG_PACKET.md` を踏襲）。

`DESIGN_PACKET.md` は **planner が作成**し、MAIN が要件台帳の校正層（人間と合意済み）との整合を確認してから dev へ渡す。

`DESIGN_PACKET.md` に含めるもの:

| 項目 | 内容 |
|---|---|
| 目的 | 1文で何をするか |
| WHY | 仕様上の由来・判断時点（dev が @why として引き継ぐ） |
| 変更範囲 | 対象ファイル・関数・追加/変更内容 |
| 制約 | 既存機能を壊さない・規約（@why 内蔵・snowball E2E） |
| 完了条件 | E2E 全 PASS・実測ログ提出など（Evidence over Claims） |
| DO_NOT | 触ってはいけないもの（範囲外・歴史的記録等） |

dev はパケットだけを読んで実装し、`AGENT_REPORT.md` に **コマンド+全出力** を Evidence として残す。

## 7. Reader の出力形式（SWMR §4 準拠）

```json
{
  "facts": [],
  "constraints": [],
  "unknowns": [],
  "conflicts": [],
  "recommendations": [],
  "evidence": []
}
```

- 生ログをメインに大量に渡さない（コンテキスト汚染防止）
- MAIN は Reader の結論を盲目的に採用しない。Reader は情報提供者であり、**最終判断は人間**が行う
- MAIN の役割は「要件と整合するか」の確認と、人間への提示（選択肢・根拠を見せて判断を仰ぐ）

## 8. モデル割り当て（重装向け）

> **軽量実装（§3.1）との違い**: 軽量運用では MAIN が実装も兼任するため、セッションの MAIN に**強いモデル**を使う。一方、重装運用（§3.2）では実装を dev サブエージェントへ委譲するため、MAIN は**薄い会話モデルでよい**。以下の表は重装実装（§3.2）を選んだ場合の割り当て。

| 役割 | モデル | 理由 |
|---|---|---|
| MAIN | **薄い会話モデルでよい** | ヒアリング・要件まとめ・ルーティング・提示のみ。作るより確かめる方が簡単なので弱くても成立 |
| research | 強いモデル | 調査品質が統合コストを決める |
| inspect | 強いモデル | 構造把握の正確さ |
| planner | 強いモデル | 設計判断・WHY の質 |
| dev | 強いモデル | 実装品質・@why 内蔵 |
| reviewer | 強いモデル | レビュー精度 |
| 人間 | 最強 | 最終判断 |

**コスト構造の逆転**: 従来（main=最強）は常時起動のセッションがずっと高い。本設計では
常時起動（main）は安く、知能は on-demand でスポーンして使い終わったら消える。
長時間自走ほどこの差が効く。

**破綻条件**: MAIN が「自分でやれる」と思い始めた瞬間に、薄い MAIN の能力がシステム全体の
天井になる。プロトコルで「MAIN はヒアリングと要件まとめだけ」を保つ規律が要。

## 9. プロンプトテンプレート（/コマンド）

| コマンド | フロー | 用途 |
|---|---|---|
| `/research <q>` | research（並列スポーン可） | 外部調査 |
| `/inspect <q>` | inspect | 既存コード調査 |
| `/plan <req>` | inspect → research → planner | 要件→調査→設計（実装なし） |
| `/dev <packet>` | dev（直列・1体） | 実装 |
| `/swmr-impl <req>` | inspect → research → planner → dev | 調査→設計→実装の直列チェーン |
| `/swmr-review <視点> <対象>` | reviewer（視点付き・先入観なし） | コードベースを特定視点から評価（同梱） |
| `/review-system [視点]` | reviewer（体制評価） | SWMR体制全体の評価（同梱） |

MAIN の基本的な流れ:
1. ヒアリング（人間と対話）→ 要件台帳にまとめる
2. 要件に応じて research / inspect をスポーン（並列）
3. planner に設計を依頼 → DESIGN_PACKET.md
4. 要件との整合を確認 → dev へ（直列）
5. dev後にE2Eを実行 → 通過したらfunction-testerへunit test追加を委譲
6. unit test後にE2E-only coverageを確認し、必要ならE2Eシナリオを追加する
7. devの成果とEvidenceを要件と照合 → 人間へ提示（判断は人間）

## 10. セキュリティ・制約

function-testerはWriterなので、Reader制約とは別に「指定テストファイルだけを書ける」ことを守る。子piプロセスには `function-tester-guard.mjs` を明示的に読み込ませ、write/editを指定テストファイル以外でブロックする。unit test実行中に生成されるcoverageやsnapshot等のファイルは、呼び出し側が実行後にgit diffで確認する。対象ソース・既存テスト・直接依存はread-onlyとして扱い、プロダクトコードを変更しない。

1. **Reader エージェント定義の `tools` に write/edit を含めない**（SWMR 絶対条件）
2. **bash は read-only のみ**をプロンプトで明示（reviewer.md の流儀: 「Assume tool permissions are not perfectly enforceable; keep all bash usage strictly read-only」）
3. **project-local agents**（`.pi/agents/*.md`）は `agentScope: "both"` で有効化するが、対話時の確認プロンプトは残す（信頼するリポジトリのみ）
4. **dev は同時に 1 体**。並列タスクに dev を含めない（chain でも直列）
5. dev はパケット範囲外を変更しない（DO_NOT 遵守）
6. **MAIN は要件台帳以外を書かない**（設計・実装・調査はサブエージェント）※重装時の原則。軽量では MAIN が実装も担う
7. **書き込みの対象分離**: 台帳（MAIN）とコード（dev）は対象が分かれており、同時並列の書き込みはない。「状態を変える主体は常に 1」の解釈で Single Writer を満たす（per-object の直列）

## 12. 検証（Evidence over Claims）

実装後の検証項目:

1. **Reader が write できないこと**: research/inspect/planner に write を試させ、拒否される/できないことを実測
2. **出力形式準拠**: 各 Reader の出力が SWMR §4 JSON 形式（または scout 形式・planner 形式）であること
3. **dev の直列性**: 並列タスクに dev を含めても同時実行されない（または運用で禁止）
4. **並列実測**: research 2 体並列スポーンが完了時間を短縮すること（ログで実測）
5. **パケット実効**: dev がパケット範囲外を変更しないこと（git diff で確認）
6. **MAIN の薄さ（重装時）**: MAIN が要件台帳以外を書いていないこと（git diff で確認）※重装時のみ適用。軽量では MAIN が実装も担うため対象外
7. **要件台帳の層構造**: 各 REQ にヒアリング層（原文）と校正層（仮定・不明点・矛盾）が交互に残っていること。思考ログが混入していないこと
8. **レビューの先入観なし**: reviewer が @why・設計文書を読まずにコード実体だけから評価していること（ログで確認）
9. **レビューの視点**: 視点（perspective）が指定され、その視点での問題が出力されていること
10. **軽量経路の検証（第一候補）**: 同一メッセージでの並列ツール実行が機能すること・視点レビューが有効な指摘を出すこと（今回の REQ-007 レビュー実験が実例）

## 13. リスク・制限

- **質問の質が結果を決める**: 何を調べさせるか・要件をどうまとめるかが MAIN の仕事。投機的調査は「後で必要になる可能性」の予測力に依存
- **コスト増**: 並列スポーンはトークン消費（モデルが強いほど）。ただしコスト削減は目的ではない。目的は文脈分離と並列読みの価値
- **投機的調査のコスト上限がない**: 並行数の上限は §2 表（最大8タスク・4並行)にあるが、**トークン費・遅延のコスト上限**はない。調査し放題で飛ぶと無制限に化ける。上限を設ける（例: 1 タスクの調査回数上限・スポーン前に「要らないもの」を絞る）
- **単発修正に使うと儀式化する**: 1 機能ごとに 7 段階フローを回すと過剰。**単発修正は AGENTS.md の「聞いて→直接やる」フローを使い、台帳・パケット・レビューは並列機会があるか長時間自走時のみ**に使う
- **文脈分離の副作用**: dev はメインの暗黙知識を持たない → パケットでの明示が必須（漏れると設計意図からズレる）
- **プロセス spawn の起動コスト**: サブエージェントごとに pi プロセスを立てる。小タスクではオーバーヘッドの方が大きい（単発調査はメインのツールで十分な場合がある）
- **MAIN の薄さが天井になるリスク**: MAIN が設計・判断に踏み込むとシステム全体が弱くなる。規律で防ぐ
- **思考ログを残そうとする誘惑**: 校正層を作る過程の思考を台帳に貼り付けるとノイズになる。残すのは原文と校正の交互だけ
- **「先入観なし」の限界（軽量実装）**: 同じセッション内で「@why を読まない」と指示しても、コンテキストに @why や設計意図が既に含まれていると影響を受ける。真の文脈ゼロは別セッション/別プロセス（重装）でのみ達成できる。軽量では「視点の固定」が主効果で、「先入観なし」は部分的な近似
- **Interview Agent は不要**: 人間はメインセッションにいる。MAIN のヒアリングがその役割を果たす

## 14. フェーズ（軽量優先）

- **Phase 1（軽量・今すぐ）**: 要件台帳規約（REQS.md 形式）をこのワークスペースに導入 + 並列ツール実行で調査。subagent 不要
- **Phase 2（軽量・運用）**: 実際のプロジェクトで台帳を運用し、REQ → パケット → コード（@why）の流れを実績で検証
- **Phase 3（重装・任意）**: 自走モードが必要になった時点で subagent extension 導入を再評価（台帳が機能して初めて機械が意味を持つ）

## 15. このワークスペースとの整合

- **AGENTS.md「Worktree: 特殊ケースのみ」**: 本システムは worktree を使わず、**サブエージェントプロセスで文脈分離**する代替手段。並列は情報収集のみ（SWMR と一致）
- **yume-spec の read-only ツール**（yspec / yhist / yui）: inspect エージェントの道具としてそのまま使える（bash read-only 経由）

## 17. サブエージェントのログ点検・暴走抑止・中間介入 (Watchdog & Intercept)

// @why: サブエージェントが長時間無反応になったり、同一エラーやツールで空回りした際に、全損キルするのではなく一時停止（SIGSTOP）してログ点検（Inspect）および中間報告（Interim Report）を求め、是正指示を与えて再開（SIGCONT）できる「調教・介入ループ」を確立する。
// @tags: SPEC, SWMR, WATCHDOG

長時間自走における「放置によるトークン浪費」と「強制終了による作業全損」の二者択一を排し、親AIおよび人間がサブエージェントの手綱を握るための運用プロトコル。

### 17.1 監視（Watchdog / 感覚器）
- **沈黙検知 (Silent Timeout)**: 指定秒数（既定 120s）アクティビティが途絶えたら検知。
- **ターン数肥大 (Turn Bloat)**: 指定ターン（既定 15 turns）を超過したら検知。
- **ツール空回り (Tool Churn)**: 同一ツール・同一引数の反復実行（既定 3回）を検知。
- **連続エラー (Consecutive Errors)**: ツール実行失敗の連続（既定 3回）を検知。
- **示唆 (Hinting)**: 強制キルではなく、異常内容と推奨アクション（`pause`, `inspect`, `report`, `resume`）をアラートとして出力。

### 17.2 介入プロトコル (Pause ➔ Inspect ➔ Report ➔ Resume / Steer)
1. **一時停止 (`pause`)**: POSIX `SIGSTOP` でプロセスを完全凍結。メモリと実行状態を保持。
2. **点検 (`inspect`)**: 直近のログ・ツール履歴・エラーを read-only で抽出。
3. **中間報告 (`report`)**: 仮説・完了作業・障害・残り予定手数を構造化して抽出。
4. **再開 / 是正 (`resume`)**: `SIGCONT` でプロセス再開。必要に応じて `steerPrompt`（追加指示）を注入。
5. **破棄 (`abort`)**: 修正不能な場合は `SIGTERM`/`SIGKILL` で安全終了。

### 17.3 ツール群
- `subagent_ps`: 登録サブエージェント一覧と健全性・異常診断
- `subagent_inspect`: 直近ログ・ツール履歴の点検
- `subagent_pause`: プロセス一時凍結 (SIGSTOP)
- `subagent_resume`: プロセス再開 (SIGCONT) + 是正ヒント注入
- `subagent_report`: 中間報告のパース・記録
- `subagent_abort`: プロセス終了
