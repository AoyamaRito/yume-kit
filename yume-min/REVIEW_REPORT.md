## 0. 結論（一言）

**「いいもの」だと思う。ただし「動く最小コア」としては完成しているが、
「全言語対応の往復（lift↔render）」に 2 つの実バグがあり、このまま実プロジェクトで
非JSファイル（特に Python / `#` 言語）に使うと壊れる。
あと 2 点、設計上の穴（refs が編集経路に乗らない / persist の成長）がある。**

つまり「**けずりの判断・思想は正しく、価値がある。実装の往復部分だけ直してから使え**」が総評。

---

## 1. 「けずり」は正しいか

**正しい。これはこの設計の最大の美点。**

- 並列化 / v00x / 契約キー / stale-write / 言語パーサ を「単一作者の透明編集」の目的から
  切る判断は、DESIGN §2 の「**単一作者に無用な装置も容赦なく切る**」という原理に一貫していて納得できる。
- 根拠の持ち方も良い。「軌跡の根っこ(V4.3)に並列は無かった」という出自の正当化は、
  「理論的に正しいから」でなく「自分の履歴で検証済みだから」という**証拠ベース**で、設計書として信頼できる。
- 切りすぎ（切るべきではなかった本質）は**見当たらなかった**。むしろ §3 で「権威(authority)」だけを
  残した判断は鋭い。並列の調整装置は切っても「真実の所在」は独立概念として残す、という切り分けは正しい。

**唯一の注記**: DESIGN §3 の「書き込みの行き先は常に正本」という単一規約の言い回しに対し、
実際の lift/render ワークフローは**書き込み先が2つ**（BlockGraph と 実ファイル）ある。
ファイルの非ブロック領域はファイルが正本、ブロック内容はGraphが正本、という二重権威が暗黙にある。
これは実害ではないが、DESIGN の物語（「単一の正本」）と実装（二重）は一言、整合を取っておく価値がある。

## 2. core.js は本当に最小で本質的か

概ねイエス。API は Block / Graph / expand / apply / domainTag / skeleton / getSurface / getImpact と
小さいのに実用に足る。ただし**直すべき穴が 3 つ**。

### 2-1 【実バグA】lift.js が `type=` 属性を読んでいない

`lift.js` の OPEN 正則はキャプチャグループが `(\S+)` と `(.*)` の**2つだけ**なのに、
attrs 抽出で **`m[3]`** を読んでいる（`m[2]` のはず）。

```js
const attrs = m[2] ? Object.fromEntries([...String(m[3] || '').matchAll(...)]...) : {};
//                                                              ^^^^ 無い。常に ""
```

- 結果: lift したブロックの `type` は**常に `'block'`** になる。
  実機プローブ: `type=function` を宣言したソースを lift すると `type = "block"`。
- 影響: 拡張時に `type` ベースの分岐（skeleton の種別、manifest 判定など）が効かなくなる。
  core 側の `parseAttrs(m[2])` は正しく `m[2]` を使っているので、**lift だけが食い違っている**。
- 修正: `m[3]` → `m[2]` の一文字。（テストにも type の検証が無く、見逃されていた）

### 2-2 【実バグB】render が `#` 言語を `//` マーカーで上書きする

`lift` は `//` と `#` 両方を受け入れるのに、`render` は開閉行を**ハードコードで `//`** で書き出す。

```js
const open  = `// >>> BLOCK ...`;
const close = `// <<< /BLOCK ...`;
```

- 結果: Python の `# >>>` ブロックを lift→render すると `// >>>` に書き換わる。
  実機プローブ: 上の出力どおり、Python ファイルに `// >>> BLOCK` が入る。
  **Python では `//` はコメントではなく除法** → ファイルが壊れる（構文エラー）。
- 影響: DESIGN §5 の「**全言語対応**」の中心セールスポイントが、非JS言語では実質壊れている。
  test 9 は本文と shell だけ確認して**マーカー記号の維持を確認していない**ため、テストに潜り込んだ。
- 修正: マーカー記号（`//` or `#`）を span に記憶して render で使い回すか、
  graph のブロックへ言語ヒントを持たせる。

### 2-3 【設計穴】refs / children が編集経路に乗らない

- `expand` は `refs:` / `tags:` を表示するが、`apply` はこれを**メタ行として捨てるだけ**
  （`META_LINE_RE` でフィルタ）。実体の refs は `applyPatch` の `opts.refs ?? h?.refs` で
  **head の値がそのまま引き継がれるだけ**。
- ∴ **expand/apply では本文(content)しか編集できない。** 依存関係の張り替え・移動・親子再編は
  この「編集経路」では絶対にできない。Graph を直接いじる必要がある。
- さらに `children` は makeVersion で保存されるが**どの関数も読んでいない**（書くだけ）。
  最小コアを謳うなら cargo（積みっぱなしの死重）で、使うなら `skeleton`/`scopeOf` に組み込む。
- これは「切った」のではなく「**単に未実装/未接続**」。単一作者でもグラフ再編は必要になることがあり、
  ドキュメントに「refs/children は Graph API で直接いじる」と明示するか、機能を足すべき。

## 3. 履歴（append-only 32版）と平文保存は十分か

**32版キャップは単一作者には十分。考え方は良い。** ただし **persist の形に実務上の落とし穴が1つ**。

- **良い点**: 直近32版を保持し `totalHistory` で総数を分かる、という設計は妥当。
  「Scrap & Build しても過去が残る」という思想と整合する。git を要求しない、
  平文 JSON で「そのまま grep / AI が読める」という動機も一貫していて正しい。
- **落とし穴**: `save()` は**全ブロック×全バージョン（最大32）を1つの JSON にダンプ**する。
  単一AIが長時間まわして多くのブロック×多くの編集をすると、**平文ファイルが際限なく肥大**し、
  読み込みコストが肥大する。これは yume-min 自身の「スナイパー読解・トークン節約」という
  中心目的（sniper reading）と**直接矛盾する**。
  - yume-lite は `readPartial` でこれを回避していたが、yume-min は読む手段（readPartial）を切ったのに
    保存手段（全履歴ダンプ）は残っている。**「読む手段を切ったのに保存で全部吐く」** は非対称。
  - 提案: save はデフォルトで**head のみ**（または明示オプションでフル履歴）にする、あるいは
    「ヘッドのみを読む loadHead」を足す。履歴は残すが**読むときは薄く**、という非対称を設計に入れる。
- 32版キャップという数字自体は妥当。単一作者の作業粒度なら十分。

## 4. 実プロジェクトで使うときの落とし穴

1. **非JSファイルを lift→render すると壊れる**（バグB）。Python/Ruby/etc では必ず再確認が必要。
2. **グラフ構造（refs/children/type）は編集ビューで直せない**（穴2-3）。プロジェクトの再編は
   Graph API を直接叩くことになり、それが「透明編集コア」から漏れる。
3. **persist の JSON が育つ**（§3）。長時間セッションだと読みが重くなる。定期的な圧縮or head読みが必要。
4. **`type` が lift 経由だと常に `'block'`**（バグA）。type を活用した機能は全部効かない。
5. **権威が2つ**（Graph と 実ファイル）。ブロック外（import 等のシェル）とブロック内で
   どちらが正本かが分かれ、両者が乖離しうる。実害は小さいが運用ルールとして認識しておくべき。
6. **リスクの小さい点**: ヘッダ hash は FNV-32bit で暗号強度は無いが、AI の「うっかり改ざん」検知には十分。
   32bit 衝突は実用上ほぼ問題にならない。

## 5. 総評

**「いいもの」と評する。** 理由は、機能の多さではなく「**けずった**」ことが正しく、
しかもその正当化が「理論」でなく「自身の軌跡からの検証済み不変項」という証拠ベースだから。
単一作者の透明編集コアとして、Block の append-only 履歴・マーカー境界・domain-tag・薄い閲覧道具・
coverage-gap 検証という選び抜かれた部品群は、どれも明快で、1ファイル一気読みで全体が見渡せる。

ただし「**ダイヤの原石が欠けている**」段階。§2 の 2 つの実バグ（lift の attrs / render のマーカー記号）が
「全言語対応」という売りを実際には裏切っており、これが直るまで実プロジェクトへの使用はできない。
加えて refs の編集不能と persist の肥大は、単一作者の長期運用で必ず当たる設計の穴。

**直すべき優先順位**:
1. **lift.js `m[3]`→`m[2]`**（1文字・type 復活）
2. **render のマーカー記号保持**（`#` 言語の往復成立）
3. persist の head 読み / refs 編集の明示化 — ドキュメント or 軽実装

これらを直せば、「単一作者の透明編集」という目的に対して、ほぼ無駄のない良コアになる。

修正は **的確・最小・テストで固められた**良好な仕上がり。
前回の 2 実バグ（型・マーカー言語）と persist の肥大という重大な 3 指摘が全て解消され、
「全言語対応の往復」と「単一作者の透明編集の長期運用」という 2 つの中心主張が実際に成立するようになった。
テストも「潜り込んだバグを落とす」方向（type 維持・`#` 維持・head モード）へ的確に強化されている。

今の yume-min は、**目的（単一作者の透明編集コア）に対して無駄のない、信頼できる良コア**と評せる。
残る refs/children の編集経路は「やるか・やらないか（Graph API 明示化）」の判断待ちで、
やるなら core の expand/apply のスコープ拡張、やらないなら DESIGN への明記が次の一手。
**「いいもの」、完了。**
